# Publication Layer

## Publication Layer

What it is: the adapter layer between jonesco's KB and the public surfaces. The KB holds claims; this layer renders public claims into each surface. Core built 2026-09-25 (see adapters below); remaining surfaces await migration or wiring.

### The rule

KB facts carry a public: marker (publication-grade: sourced, approved, no confidential leakage) — only marked facts flow to surfaces. Gated publish: agents stage surface changes from the KB, Mike approves once, then they fan out. Nothing publishes unattended (a typo must not go live on six domains). One direction: KB → surfaces. A surface never edits the KB directly; corrections enter through a maintenance pass, per SCHEMA.

### Adapter: Distills RAG (pilot — built 2026-09-25, staged for approval)

The cheapest leg, proven end to end. Correction to the original design: the live chain is not ~/dev/distill-app (that is the multi-tenant SaaS). It is ~/dev/MJ_Online/mj-chatbot-backend — a dedicated Cloudflare Worker. Mechanism. mj-chatbot-backend/scripts/kb-to-rag.mjs reads KB//*.md directly from the vault (no content duplication), strips frontmatter and Sources/History sections, chunks each page by ## section into the distill RAG JSONL schema (narrative entries; topic from page type; source: = the KB path, so every claim stays traceable), and writes only into mj-chatbot-backend/staging/: knowledge.jsonl, knowledge-data.js (the CommonJS module the Worker ingests, same format src/knowledge-loader.js produces), staged.diff, and stage-report.md (human-readable summary for the approval gate). Live chain it feeds. mikejones.online pages → distill-chatbot-widget.js (RAG_CHATBOT_CONFIG → mj-chatbot-backend Worker /chat) → Worker loads src/knowledge-data.js at boot → src/rag-retrieval.js keyword scoring → Claude. The bot changes only when knowledge.jsonl + src/knowledge-data.js are replaced AND the Worker redeploys — apply and deploy are deliberate human steps after approval. How to run. ` cd ~/dev/MJ_Online/mj-chatbot-backend node scripts/kb-to-rag.mjs # dry run, prints summary, writes nothing node scripts/kb-to-rag.mjs --stage # writes staging/ only; live files untouched ` After Mike approves: `cp staging/knowledge.jsonl knowledge.jsonl && cp staging/knowledge-data.js src/knowledge-data.js && npm run build && npm run deploy (from mj-chatbot-backend/`). What it excludes (vault CLAUDE.md rule 1 — nothing confidential reaches index.md, log.md), frontmatter, Sources/History sections, blockquotes. First run: 12 pages → 44 entries; 2 confidential pages excluded; 11 lines redacted; automated scan of staged output found 0 marker hits. Pilot decision point (for the approval gate). The pilot card's gate is the confidential filter above. The public: marker regime (default-deny) is stricter — honoring it today would nearly empty the RAG, since most KB pages do not carry public: yet. At approval Mike picks: (a) run this leg on the confidential filter now, tightening to public: gating as pages get marked (adapter default), or (b) hold until marking is done. Switching is a small change in chunkPage(). Coverage note. The live 202-entry knowledge.jsonl (generated 2026-06-26) predates the vault KB and carries stale facts (e.g. "24+ years"). Replacing it with KB claims is the point of this layer, but until the KB backfill catches up the bot answers only from KB pages — Mike approves knowing that.

### Adapter: mikejones.online content.ts (built 2026-09-25, staged for approval)

Second leg. ~/dev/MJ_Online/site/scripts/kb-to-content.mjs reads KB//*.md directly (read-only input; the generator never writes into KB/), keeps only and renders them into a KB:BEGIN/KB:END region at the end of site/src/lib/content.ts — a generated region inside the hand-maintained file. Everything outside the region stays hand-edited; the page-by-page mapping (generated vs hand-maintained, and why) lives in the generator's FIELD MAP header comment. Today the only public: yes page is ccar-f-certification → generated export certifications (name, abbrev, issuer, issued/issuedDisplay, expires, proofUrl, scope — parsed from the page's Fact|Value table with per-field provenance). resume.astro renders it in Recognition; the hardcoded cert line How to run. ` cd ~/dev/MJ_Online/site node scripts/kb-to-content.mjs # dry run — summary only, writes nothing node scripts/kb-to-content.mjs --stage # writes site/content.staging/ ONLY node scripts/publish-content.mjs # plan — what --apply would do node scripts/publish-content.mjs --apply # AFTER Mike approves the staged diff: ` The commit is the approval gate: publish-content.mjs commits after approval and never pushes — git push is Mike's manual step (Cloudflare Pages auto-deploys on push to main). First publish includes the plumbing (generator, publish helper, resume.astro, site/.gitignore); later publishes need only site/src/lib/content.ts. Safety rails: apply refuses when the working tree's content.ts has hand-edits staging didn't start from, builds before committing, and verifies the commit contains exactly the intended paths. First run (2026-09-25). 12 KB pages read → 1 cert entry (ccar-f-certification). Staged diff = introduction of the generated region only; every generated value already matches the hand-maintained file (the cert work landed on the site in the t_90718efd run, before the KB backfill — the untouched), the rendered resume cert line is unchanged, and a negative test confirms apply refuses on a drifted working tree. To add a generated field. Mike marks the source page public: yes, then an adapter is registered for it in kb-to-content.mjs (the ADAPTERS table). A public: yes page with no adapter is reported as unmapped and emits nothing — default-deny is preserved.
